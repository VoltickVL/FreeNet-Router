# FreeNet Router — обязательные проектные инструкции

## Фиксированная цель

**Проект:** FreeNet Router, репозиторий `VoltickVL/FreeNet-Router`. **Источник истины:** GitHub. Roadmap — issue **#5**, журнал — issue **#7**.

**FreeNet 0.9 — новое самостоятельное приложение Control Center над ОРИГИНАЛЬНЫМИ XKeen + Xray-core.** Его задача — заменить FreeNet 0.8 без переноса архитектурного наследия, обеспечить установку, добавление/обновление пользовательской VPN-подписки, управление штатными функциями, проверку результата и обновление. Эталонный продуктовый контракт и критерии выпуска: [v09/PRODUCT_CONTRACT.md](v09/PRODUCT_CONTRACT.md).

**Решение Management 07.11.2026 — закреплённый ориентир:** FreeNet 0.9 разрабатывается против **XKeen 2.2 Beta**, не против 2.1 Stable. Перед любой интеграцией нужно проверить точный upstream 2.2 Beta tag/commit и соответствующие CLI/init/config/updater. Предположения и успешные тесты для 2.1 не доказывают совместимость; неподтверждённое действие = STOP. **Новое решение Management 07.11.2026:** первый canary — **HOME** сегодня, затем PORTABLE, затем WORK; HOME не менять автоматически, только после read-only preflight и контролируемого safe cutover. Это заменяет прежний приоритет PORTABLE-first. Это не разрешение обновлять установленный XKeen автоматически.

**Важное уточнение Management 07.11.2026 (DNS/чистая установка):** целевой FreeNet 0.9 не должен наследовать собственный DNS proxy/Split DNS, AutoVPN, cron или DNS/PBR orchestration старой 0.8. Сохраняются **семантика пользовательских DIRECT/VPN/ISP правил** и приватная подписка, но не старые технические DNS-зависимости. Legacy 0.8 встроила DNS-specific `dns-direct`/`dns-vless`/`dns-out` в стандартные Xray `02_dns.json`, `04_outbounds.json`, `05_routing.json`. Поэтому перед чистой установкой 0.9 конфигурация требует provenance/dependency audit; не копировать/очищать её автоматически. 0.9 управляет только штатными native XKeen/Xray функциями. HOME сейчас работает на 0.8+XKeen 2.1+Xray 26.10.31, сам 0.9 не установлен, штатное обновление XKeen до 2.2 Beta ещё не применено.

### Непересматриваемые границы

1. **Xray — единственное VPN/proxy/DNS/routing ядро. XKeen — единственная штатная интеграция с Keenetic/Netcraze**, сетевыми хуками, IPSET и управлением core. FreeNet — UI, orchestration и минимальные адаптеры к поддерживаемому upstream API/CLI/config.
2. **Нет собственного AutoVPN, Live Pool, баланcировщика, cron обновления GeoData, DNS-прокси или iptables/ipset writer.** Сначала проверить точную установленную версию и реализованный в upstream механизм. Xray balancer/Observatory и XKeen `-sb` — штатный выбор сервера; GeoFile/GeoIP/GeoIPSET — штатная задача XKeen `-ug`/`-ugc` либо отдельный native Xray geodata (ОДИН владелец расписания).
3. **Не переносить и не рефакторить backend 0.8** в `v09/`. Текущие `freenet-ui/`, `scripts/`, `bootstrap.sh`, `install.sh`, `deploy/` — legacy, не основа версии 0.9. Не импортировать их Go-пакеты и не привязывать новый Control Center к их helpers.
4. **0.9 — полноценный управляющий продукт, не read-only просмотрщик.** Preview/staging обязаны быть read-only лишь до аутентификации, планирования, приёмки и безопасного переключения. Финал — собственная подписка, настройка native VPN/ISP/DNS/routing, запуск/остановка/restart XKeen/Xray и их штатные обновления **через браузер**. **Без разделов Backup/Restore/Recovery и отдельной подсистемы резервных копий.**
5. **Чистая ЗАМЕНА FreeNet 0.8 → 0.9:** две версии FreeNet могут временно находиться на диске лишь для проверки новой панели, но **одна** работает как управляющая служба и веб-панель. 0.9 — новый слот `/opt/freenet-v09/`; после приёмки старые FreeNet 0.8 binary/init/managed-cron/helpers удаляются из активной системы. Не создавать параллельный Backup Center или пользовательский архив. **Оригинальные XKeen + Xray, их настройки/списки/GeoData/credentials и существующий XKeen UI неприкосновенны.** Никаких параллельных schedulers, двойных balancer overrides, duplicate netfilter или незаметного DIRECT при обязательном VPN.
6. **Каждая mutation:** сначала выяснить штатный upstream механизм, проверить native конфигурацию и expected delta → контролируемое минимальное применение → проверить runtime и клиентский результат. **Без собственной backup/restore системы.** Для опасного изменения использовать временные средства атомарной записи/отката только когда без этого нельзя гарантировать сохранность настроек; при неизвестном состоянии STOP, не выполнять следующую mutation. Текущие credentials и конфигурации не терять и не выводить в PR/log/Issue.
7. **Установка без «танцев с бубном»:** Entware → bootstrap → браузер → определение existing/clean/partial → точечная установка необходимого → Browser Setup. Existing working XKeen/Xray не переустанавливать, partial/unknown = STOP. SSH только для действительно недоступных иначе runtime-фактов; не заменять работой по SSH продуктовые функции.
8. **Один полностью принятый релиз `v0.9.0`.** Внутренние PR/CI допустимы, но не выпускать публичные 0.9.0-dev/beta и не создавать «миллион патчей» вместо завершённого рабочего сценария. Рабочую 0.8, XKeen/Xray и настройки не изменять без контролируемой приёмки; первый canary — HOME по новому прямому решению Management, затем PORTABLE и WORK. HOME сейчас read-only подтвердил XKeen 2.1 Stable + Xray 26.10.31 + FreeNet 0.8, поэтому STAGING_ONLY до совместимости/cutover.
9. **Без самодеятельности:** не добавлять ограничений, скрытия IP/доменных имён в обычных Xray labels, лишних адаптеров или fallback-алгоритмов без конкретной подтверждённой причины. Не переносить продуктовую логику на площадки HOME/WORK/MOM: первичны ISP + routing policy.
10. **Исполнитель — ChatGPT**, не «автор ТЗ для разработчика». Получив однозначную задачу, сам проверить GitHub HEAD/PR/issues, изменить код, написать тесты, дождаться terminal CI, проверить diff, merge, журнал #7, Roadmap #5, закрыть execution issue. Пользователю сообщать факты, блокер и необходимость действия лишь если это действительно требуется.

**ОБЯЗАТЕЛЬНО ПЕРЕД КАЖДОЙ НОВОЙ ЗАДАЧЕЙ:** спросить себя: «Это нужно для лёгкой оболочки XKeen/Xray, добавления подписки, управления штатными функциями или проверки результата? Уже есть такой upstream механизм? Не добавляю ли снова backup/recovery/AutoVPN-комбайн?» Если функция не необходима — не реализовывать.

### Предпроверка каждого PR в ветку 0.9

- Связь с конкретным пунктом `v09/PRODUCT_CONTRACT.md` и явно определённая upstream-ответственность.
- Изменения только в `v09/**`, профильном CI и этих инструкциях. Любая правка legacy-дерева — новая явно разрешённая самостоятельная задача, **не** случайный побочный эффект 0.9.
- Targeted tests, сохранность работающего XKeen/Xray и отсутствие второго владельца VPN/DNS; правдиво различать конфигурацию, runtime и доказанный клиентский HTTPS egress.
- Установка/обновление сторонних XKeen/Xray запрещена в том же цикле, что переключение FreeNet 0.8 → 0.9.
- После успешного цикла фиксировать точные PR, CI, SHA и release в #7; отражать изменение стадии в #5; закрывать execution issue.

**Если новое предложение противоречит этим правилам, не реализовать его молча: выбрать штатную возможность XKeen/Xray либо остановиться с конкретным техническим основанием.**
