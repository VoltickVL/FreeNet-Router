# Контракт AutoVPN: минимальные проверки, реальное качество и безопасная смена

Статус: согласованный продуктовый принцип Management, 30.10.2026. Применять при каждой доработке AutoVPN; первоисточник обсуждения — требование обеспечить стабильный Instagram/видео/ChatGPT, а не красивое значение ping или факт переключения. Это контракт поведения, а не обещание воспроизводить Instagram через HTTP HEAD.

## Цель

**VPN работает хорошо → FreeNet не вмешивается. Повторные медиалаги → ограниченный быстрый поиск → подтверждённо хороший кандидат → одна защищённая смена → короткая проверка результата → обычный мониторинг.**

1. Лёгкий периодический read-only health. Медиа-измерения ограничены частотой и трафиком, не конкурируют с deep scan. Одного лагового сегмента недостаточно для смены VPN.
2. После повторной подтверждённой деградации одного и того же активного профиля запускать **один** ограниченный подбор. RTT — только недорогой фильтр, не критерий окончательного выбора. Сначала наиболее перспективные кандидаты; продолжать по списку лишь при недоступных/недостаточно хороших. Не устраивать бесконечный полный перебор. Сравнивать реальную последовательную передачу медиаданных, HTTP-отклик и jitter; не считать высокий aggregate Speedtest доказательством отсутствия буферизации.
3. Уже достоверно измеренный кандидат не должен повторно проходить идентичные дорогие проверки. Короткий свежий admission необходим **непосредственно перед mutation**, если это гарантирует, что измеренный путь по-прежнему существует и работает. Снимать лишние дубликаты, не отменять транзакционную безопасность.
4. Только при подтверждённо лучшем кандидате выполнить сохранение предыдущего состояния → проверку точной identity/config → одно контролируемое применение → bounded HTTPS acceptance. При реальном отказе восстановить предыдущую рабочую конфигурацию. При FAILED/UNKNOWN rollback — STOP до уточнения состояния. Не выполнять «возврат на предыдущую страну» просто из-за колебания скорости.
5. После успешной смены обычный лёгкий мониторинг возобновляется сразу, но следующий **тяжёлый** подбор не должен стартовать через несколько минут лишь потому, что cooldown отсчитывался от начала прошлого много-минутного скана. Опорное время — **завершение** реальной попытки. BUSY/ранний выход без скана не расходует эту паузу. Подтверждённая полная потеря VPN использует отдельный аварийный путь и не блокируется QoE-паузой.
6. Главная показывает VPN/RTT/стабильность и честную измеренную скорость с датой замера. Отсутствие скорости не означает отключённый VPN. Не заменять полноценный Speedtest маленькой QoE-пробой и не выдавать 8–10 Мбит/с из короткого сегмента за пропускную способность канала 300 Мбит/с. Адаптивный extended Speedtest для быстрых каналов сохраняется.
7. Не менять ISP/DNS/routing policy, existing XKeen/Xray, credentials в цикле медиаоптимизации. Не заставлять Management запускать SSH, ручные бенчмарки или разбираться с lock-файлами.
8. Контрольный HTTPS-сегмент — **суррогат QoE**, не прямое подтверждение воспроизведения Instagram Reels, ChatGPT, QUIC/IPv6 или поведения браузера пользователя. Клиентские наблюдения, например «Милан хуже Франции по Instagram», — серьёзный сигнал на расследование, но не доказательство конкретного root cause без парных сопоставимых замеров.

## Границы реализации

- Разделять **медиа-QoE** (короткие последовательные GET) и **скорость канала** (канонический aggregate Speedtest, расширяемый для быстрых линий). Не менять формулу Speedtest ради AutoVPN.
- **Независимость медиаисточника:** при подозрении на медиалаг основной ограниченный Cloudflare GET должен быть подтверждён независимым HTTP-body GET ровно на 1 МиБ из OVH через **тот же** SOCKS/Xray VPN-путь. Здоровый watchdog не скачивает дополнительный файл. Кандидат на media-only AUTO обязан пройти обе независимые передачи. При отказе, неполной передаче или противоречии источников — **UNKNOWN, без mutation**. Не считать этот тест реальным Instagram Reels/QUIC.
- **Антифлап:** после успешной смены логического VPN новый *media-only* Top-3 поиск запрещён на **60 минут**, даже если короткие сегменты снова ухудшились. Лёгкий мониторинг продолжает работать. Достоверный полный outage идёт по отдельному emergency recovery; подтверждённые сервисные или latency инциденты используют собственные правила. Пауза по завершению реально начатого heavy scan сохраняется для неуспешных поисков.
- Короткий список по фактическому логическому VPN-пути, а не raw TCP к общему ingress; несколько профилей могут разделять IP:port, но иметь разные exit/Reality identities.
- Настройки паузы, допустимого качества, количества кандидатов меняются только с targeted тестами и фактом аппаратного поведения; не ослаблять их «на глаз».
- Одна тяжёлая операция за раз; read-only light health не должна создавать дополнительные bulk GET во время сканирования.
- Acceptance: **DEGRADED → MEASURED CANDIDATE → SWITCHED → POST-APPLY CONNECTIVITY → клиентский QoE/без частых повторных сканов**, либо точный safe STOP с PRIMARY ERROR и rollback. CI доказывает контракт кода, не реальную скорость Instagram.

## Обновления Xray/XKeen/FreeNet — отдельный контракт

Штатная проверка окружения → загрузка и проверка артефакта → snapshot → безопасное применение → postcheck → terminal receipt/rollback. Existing healthy stack и credentials сохраняются. Не убирать защиты, которые предотвращают потерю доступа, но избегать повторных дорогостоящих проверок и неопределённых вечных блокировок: FreeNet сам показывает конкретную причину и выполняет безопасное восстановление, когда факты достаточны. При UNKNOWN/FAILED rollback — STOP без слепых рестартов. Никакого SSH как обязательного шага установки и обновления.
