# FreeNet Router — подключение ChatGPT через Secure MCP Tunnel

**Статус на 10.10.2026:** в FreeNet имеется локальный read-only MCP-сервер и временное разрешение (15 минут). Прямое подключение ChatGPT **не настроено**. Этот документ описывает проверяемые условия подготовки, а не отчёт о выполненном runtime-подключении.

## 1. Принцип безопасности

- Связь устанавливает **официальный OpenAI tunnel-client** исходящим HTTPS к `api.openai.com:443`. Ни веб-порт FreeNet, ни SSH, ни Xray не открываются во внешнюю сеть.
- FreeNet MCP слушает **loopback самого роутера**. LAN-клиенты и другой узел LAN не могут обращаться к этому endpoint напрямую — так задумано. Отключать эту проверку ради коннектора запрещено.
- Машинные вызовы требуют отдельного краткоживущего Bearer с правом `read:diagnostics`. Browser session/cookie не является machine credential. Разрешение можно немедленно отозвать в «Администрировании».
- Доступны только `get_status`, `get_component_health`, `test_route` и `get_recent_journal` (последний пока явно `available=false`). Нет shell-команд, переключения VPN, перезапуска Xray или редактирования конфигураций.
- Результат `test_route` содержит **CONFIG_ONLY/UNKNOWN** и **NOT_OBSERVED**. Он не доказывает фактический outbound для LAN-клиента.

## 2. Автоматическая проверка FreeNet

«Администрирование» → «Проверить подключение ChatGPT» использует авторизованный GET `/api/admin/connector/readiness`.

FreeNet сообщает архитектуру, предполагаемый localhost MCP, доступность временного разрешения и причину STOP. **Не интерпретируйте `OFFICIAL_BINARY_ARCH_SUPPORTED` как готовый рабочий tunnel-client.** Установку, ABI Entware, размер памяти, ключ OpenAI, association workspace и действующий tunnel endpoint это поле не подтверждает.

| Архитектура роутера | Официальный tunnel-client | Безопасный следующий этап |
|---|---|---|
| Linux ARM64 / AMD64 | Сборки опубликованы | Проверить совместимость ABI/ресурсов на устройстве, установить только проверенный бинарник с контрольной суммой; затем настроить исходящий туннель |
| Linux MIPS / MIPSEL / ARM32 | Официального бинарника нет | **STOP** для установки на роутер. Нужен доверенный Linux AMD64/ARM64 узел с отдельным проверенным защищённым мостом к FreeNet; мост пока не реализован |
| Иная / неизвестная архитектура | Не подтверждена | **STOP**, без догадок |

Источник по официальным сборкам: https://github.com/openai/tunnel-client/releases/latest

## 3. Что требуется от OpenAI Platform и ChatGPT

1. В своей OpenAI Platform организации иметь права **Tunnels Read + Manage** (создать endpoint) и **Read + Use** (запуск и выбор). Создать приватный `tunnel_id` в https://platform.openai.com/settings/organization/tunnels. Данные `tunnel_id` и секреты **не вставлять в GitHub issue, PR, журнал или этот чат**.
2. Привязать туннель к нужному **ChatGPT workspace**, иначе он не появится при создании собственного MCP plugin.
3. Получить отдельный **runtime API key** для `tunnel-client` (не admin key для CRUD). Использовать приватное хранилище секретов; не передавать ключ через URL или shell history.
4. На поддерживаемой машине, внутри доверенной сети, проверить путь к приватному MCP и запуск официального `tunnel-client`. Документированная процедура: `tunnel-client init`, `tunnel-client doctor --explain`, `tunnel-client run`. Для localhost HTTP MCP применим параметр `--mcp-server-url http://127.0.0.1:1001/mcp` **только если клиент действительно работает на том же роутере**, сервис слушает этот порт и согласован механизм Bearer-авторизации. Не переносить localhost URL на другой компьютер: это будет уже его loopback.
5. В ChatGPT: **Plugins → Add custom MCP server → Tunnel**. Выбрать связанный с workspace tunnel, настроить требуемую авторизацию, подтвердить разрешения и подключить созданный plugin. Это действие требует разрешения пользователя в ChatGPT.
6. Проверить фактическую готовность `tunnel-client doctor --explain` или `/readyz`, затем `initialize`, `tools/list` и read-only `get_status`. После проверки отозвать временное разрешение и подтвердить отказ следующего запроса.

Официальная документация: https://developers.openai.com/api/docs/guides/secure-mcp-tunnels и https://github.com/openai/tunnel-client/blob/master/docs/configuration.md

## 4. Блокеры, которые нельзя обходить

- **MIPS:** нельзя устанавливать Linux ARM64-binary на MIPS или расширять localhost endpoint до LAN/WAN. Для размещения официального клиента на отдельном узле нужен отдельный scoped PR по взаимной аутентификации и защищённому мосту либо подтверждённый совместимый клиент для MIPS.
- **15-минутный Bearer:** текущая схема не предоставляет бесконечную авторизацию туннеля; после TTL вызовы получают отказ. Не хранить plaintext access token в GitHub, в небезопасном файле, в URL или в логах. Полностью управляемая ротация и безопасный secret injection — отдельный этап, а не ручной обход.
- **Ключи OpenAI:** endpoint нельзя создать автоматически через GitHub-код без полномочий организации OpenAI. Management выполняет только необходимое связывание/выдачу прав в своей Platform и ChatGPT; FreeNet должен делать остальную диагностику продуктом.
- **Runtime UNKNOWN:** если состояние маршрутизации/VPN или rollback не подтверждено, дополнительные mutation не выполнять. Настройка туннеля не должна изменять Xray, XKeen, DNS или firewall.
- **Подтверждение доступности:** отсутствует до фактического пробного вызова из ChatGPT. Исходные файлы, CI и локальный readiness не заменяют эту проверку.

## 5. Дальнейшая реализация

1. Secure lifecycle официального клиента на подтверждённой поддерживаемой архитектуре либо доверенный bridge на отдельном узле с независимым security review.
2. Managed setup в браузере, проверенный конфигурационный plan, запрет утечек, безопасное provision/revoke и автоматическая проверка готовности без raw terminal.
3. Реальная end-to-end приёмка MCP из ChatGPT на разрешённом устройстве. После неё — эксплуатация в рамках `read:diagnostics` без SSH.
