## 6. УСТАНОВКА И ПЕРВОНАЧАЛЬНАЯ НАСТРОЙКА

### Новый роутер

Keenetic/Netcraze → USB + Entware → bootstrap → определение окружения → установка недостающих компонентов → FreeNet Control Center → Browser Setup → VPN → ISP/DNS → Routing → Automation → финальная проверка.

### Действующий роутер

Entware + существующий XKeen/Xray/XKeen UI → bootstrap → определение рабочего стека → сохранение исправных компонентов, пользовательских конфигураций и credentials → установка только необходимого → FreeNet Control Center.

Установщик обязан определять:

- что уже установлено;
- что действительно исправно;
- чего не хватает;
- что допустимо безопасно установить;
- какие компоненты нельзя заменять;
- как сохранить текущую работающую конфигурацию;
- существуют ли частичные или противоречивые состояния.

**Полностью рабочий existing stack не переустанавливать.**

Partial/unknown state = STOP с конкретной причиной.

Не угадывать версии, пути, init-скрипты или состояние runtime.

SSH preflight не должен быть обязательным этапом стандартной установки.

## 7. ПРОДУКТОВАЯ МОДЕЛЬ ISP + ROUTING POLICY

Архитектура маршрутизации строится вокруг:

**Internet Provider → ISP Profile → Routing Policy → VPN/DIRECT/BLOCK.**

Не строить код и продуктовые правила вокруг названий HOME, WORK, MOM или других площадок.

Каждый роутер использует определённый ISP profile и соответствующие подтверждённые политики.

Актуальные ISP profiles, baseline и сервисные исключения получать из Roadmap #5 и реальных конфигураций.

Не наследовать настройки одного оператора другому без подтверждения.

Custom должен предоставлять ручную экспертную политику.

Не создавать правила для конкретных сервисов по предположениям или непроверенной памяти.

При изменении policy проверять фактическую маршрутизацию, а не только содержимое файлов.

## 8. ДОСТОВЕРНАЯ ДИАГНОСТИКА VPN, DNS И ROUTING

FreeNet должен различать:

1. Работоспособность интернет-провайдера.
2. Доступность VPN endpoint.
3. Работу процесса Xray.
4. Корректность Xray configuration.
5. Фактический перехват трафика Keenetic/XKeen.
6. Применённые kernel routing/netfilter rules.
7. Маршрут конкретного клиентского устройства.
8. Работу DNS.
9. Прикладную доступность сервисов.

**Успешный Xray probe не означает, что клиентский трафик проходит через VPN.**

**Работающий DNS через VPN не доказывает, что HTTPS также идёт через VPN.**

**Наличие netfilter hook-файла не доказывает наличие активных kernel rules.**

Проверять фактический результат на подходящем уровне.

Не показывать «VPN работает» как полное подтверждение, если клиентский VPN egress неизвестен.

При недоступности факта отображать UNKNOWN, а не SUCCESS.

Диагностика должна помогать обнаружить PRIMARY ERROR, а не создавать множество второстепенных проверок.

Не переключать VPN-сервер наугад при неисправности локального перехвата или маршрутизации.

## 9. AUTOVPN И ОТКАЗОУСТОЙЧИВОСТЬ

AutoVPN должен обеспечивать устойчивое соединение, а не максимальное число переключений.

Основные требования:

- различать VPN failure и ISP failure;
- учитывать реальную доступность приложений;
- обнаруживать деградацию качества;
- исключать ложные срабатывания;
- использовать подтверждение устойчивого отказа;
- соблюдать cooldown и hysteresis;
- избегать переключений между одинаково плохими серверами;
- сохранять последнее подтверждённое работоспособное состояние;
- не перезапускать Xray без необходимости;
- поддерживать безопасный failover;
- останавливаться при неизвестном или противоречивом runtime state.

Одиночный timeout, ping или успешный speedtest не должен автоматически определять итоговую оценку VPN.

Использовать подходящие механизмы watchdog, balancer и health-check из XKeen Panel и Xkeen UI после проверки их совместимости с FreeNet.

Реальное качество пользовательского интернета важнее синтетического результата проверки скорости.

## 10. БЕЗОПАСНОСТЬ RUNTIME И ROLLBACK

Любая операция, изменяющая VPN, DNS, routing, Xray, XKeen или сетевые параметры, должна иметь по возможности:

1. Preflight.
2. Plan.
3. Expected delta.
4. Backup/snapshot.
5. Candidate validation.
6. Controlled apply.
7. Post-apply acceptance.
8. Rollback.
9. Terminal result.

PRIMARY ERROR и rollback result фиксировать отдельно.

**ROLLBACK FAILED или UNKNOWN = STOP.**

Никакой следующей mutation до установления фактического состояния.

Не выполнять blind retry.

Не удалять locks без доказательства их устаревания.

Не запускать лишние restart/reboot.

Не объявлять операцию успешной только по HTTP 200, завершению команды или успешному сохранению файла.

Проверять фактический результат, включая работу клиентского интернета там, где изменение может на него повлиять.

Любое диагностическое временное изменение должно иметь ограниченную область действия и контролируемое восстановление.

**Никогда не оставлять неконтролируемые фоновые операции, способные позднее изменить рабочую конфигурацию.**

## 11. SSH И УДАЛЁННОЕ УПРАВЛЕНИЕ

SSH использовать только если для следующего технического решения требуется runtime-факт, который невозможно получить через GitHub, bootstrap, doctor, Browser Setup или Control Center.

Перед SSH определить:

- какой факт отсутствует;
- почему продукт его не предоставляет;
- зачем этот факт необходим.

Предпочитать read-only диагностику.

SSH mutation — исключительное действие при аварийной или диагностической необходимости, с отдельным обоснованием, планом и откатом.

Не превращать SSH в основной способ эксплуатации.

Не заставлять Management повторять команды, которые ChatGPT может безопасно выполнить через авторизованные инструменты.

При работе через Remote Desktop Commander не отправлять команды в окно без подтверждения целевого процесса и терминала.

Не управлять графическим интерфейсом наугад.

Выявленные пробелы диагностики и управления постепенно устранять в самом FreeNet.

## 17. ПОЛИТИКА BETA И STABLE

Текущую ветку разработки, номер следующего выпуска и политику rollout определять по GitHub и Roadmap #5.

Общий принцип:

**Сначала Beta → испытания → подтверждённая стабильность → Stable.**

Не переключать оборудование постоянно между Beta и Stable.

Новые функции и исправления сначала проверять на назначенных тестовых площадках.

Эксплуатационные площадки не использовать для необязательных экспериментов.

Сохранять проверенную рабочую Beta, если новая версия ещё не прошла необходимые испытания.

Stable выпускать из подтверждённого кода, а не просто переименовывать очередную Beta.

### Критерии Stable

Необходима подтверждённая устойчивость:

- реального клиентского интернета;
- VPN/DIRECT маршрутизации;
- DNS;
- перехвата XKeen;
- Xray runtime;
- AutoVPN и Failover;
- обновлений;
- rollback/recovery;
- работы после перезагрузки;
- длительной эксплуатации без критических сбоев.

Конкретные измеримые критерии, длительность приёмки и целевые площадки устанавливаются в Roadmap #5.

Management определяет, какие роутеры используются для испытаний, а какие должны оставаться на проверенной версии.

Не считать успешно пройденный CI достаточным основанием для выпуска Stable.

---

### Актуальная площадка испытаний — по местонахождению Management (решение 03.11.2026)

Основная площадка **не закреплена навсегда за WORK**. Определять место испытаний из последнего прямого сообщения Management, не угадывать по IP, часовому поясу, геолокации или старым записям:

- Management **дома** → основной испытательный роутер **HOME**.
- Management **на работе** → основной испытательный роутер **WORK**.
- Management **в командировке** → основной испытательный роутер **Portable**.
- **MOM** — эксплуатационный роутер, не используется для экспериментов и автоматических обновлений.

На 03.11.2026 Management прямо сообщил: **«сейчас я дома»**, поэтому текущая площадка — **HOME**. При следующем прямом сообщении об изменении местонахождения переключить приоритет испытаний; не делать долгосрочный вывод из этой разовой отметки.

**Выбор площадки не снимает технические STOP-гейты** и не даёт права менять сеть под видом диагностики. Read-only acceptance — по доступным штатным инструментам FreeNet. Любое обновление, VPN/DNS/routing apply, restart или failover-тест с mutation допускается только после отдельного безопасного plan/snapshot/candidate validation, post-apply acceptance и доказанного rollback. При FAILED/UNKNOWN — STOP без обходных SSH-команд. В частности, Portable с известным FAILED_UNKNOWN не обновлять до разрешения блокировки. HOME, когда Management дома, может быть текущей испытательной площадкой, но ранее действовавший freeze не отменяет этих ограничений автоматически. Для изменения работающих маршрутов нужен отдельный контролируемый план.

### Обязательный отчёт в текущем чате после каждого нового релиза

После **каждого официально опубликованного** FreeNet release (не после одного лишь merge или queued CI) ChatGPT обязан **сразу написать в этот чат** краткую фактическую сводку:

1. Версия релиза и ссылка на GitHub Release.
2. Какие пользовательские функции и исправления реально вошли в выпуск.
3. PR/merge SHA, terminal Release CI, проверка артефактов и SHA256SUMS.
4. Что изменено только в коде/релизе, а что фактически установлено и проверено на роутере.
5. Текущая площадка испытаний по сообщению Management, оставшиеся STOP и конкретный следующий шаг.

Не объявлять выпуск опубликованным до terminal Release CI SUCCESS и наличия release tag/assets; не смешивать публикацию с подтверждённой аппаратной приёмкой. Этот отчёт обязателен даже если действий Management не требуется.
