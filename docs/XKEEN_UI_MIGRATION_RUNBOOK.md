> **АКТУАЛЬНЫЙ ДОКУМЕНТ.** FreeNet Router 0.8 снят с эксплуатации на HOME и WORK. Разработка FreeNet 0.9, Browser Setup, собственного Split DNS, AutoVPN, watchdog и других функций **прекращена**. Код FreeNet в этом репозитории — исторический архив, **не инструкция к установке**. Продолжаем эксплуатацию и миграции только штатными **XKeen + Xray + Xkeen UI umarcheh001**. ## 1. Источники истины и правила безопасности

- [XKeen](https://github.com/jameszeroX/XKeen), [Xkeen UI](https://github.com/umarcheh001/Xkeen-UI), [официальная DNS-over-VLESS](https://github.com/umarcheh001/Xkeen-UI/blob/main/docs/dns-over-vless.md), [официальные профили установки](https://github.com/umarcheh001/Xkeen-UI/blob/main/docs/modular-panel-stage7-installer-profiles.md).
- На уже принятых HOME/WORK: **XKeen 2.1 Stable**, **Xray 26.10.31**, **Xkeen UI 3.0.2**, Entware. Новые роутеры сначала аудировать; не переустанавливать исправные XKeen/Xray и не обновлять ядро «ради новой версии».
- Сохранять рабочий доступ в интернет. Перед каждой рискованной правкой фиксировать конкретную проблему/ожидаемый результат, иметь *локальную точку отката*, делать `xray run -test` на кандидате и после изменения, проверять процессы, firewall, DNS, HTTPS и реальные DIRECT/VPN.
- **Не переносить** с других площадок: MAC/IP, интерфейсы WAN/LAN, IP DNS провайдера, hostname, credentials, содержимое подписки, REALITY/VLESS UUID/ключи, адреса внутренних сервисов, готовый routing JSON.
- Административная веб-панель: локально обычно порт **8088**; не публиковать напрямую в Интернет без отдельной модели доверенного доступа (VPN, ограничения/авторизация). Не записывать приватные URL панели, VPN или пароль в GitHub.
- Предпочитать штатный браузерный UI. Entware/CLI — при недостаточности UI, для runtime-аудита и отладки. Никаких новых фоновых сервисов, «сторожей», пользовательских прокси/DNS-движков и cron вне официальных XKeen/Xkeen UI.

## 3. Порядок миграции нового роутера (PORTABLE → затем у мамы)

### Шаг 0. Определить железо и фактическую сеть

1. Уточнить **точную модель** (например KN-1011/1012 или KN-1811), архитектуру Entware `uname -m`, разрядность бинарника, версию KeeneticOS, физическую **ОЗУ**, USB/Entware storage и свободное место.
2. Зафиксировать `MemTotal`, `MemAvailable`, SwapTotal/SwapFree, RSS Xray, Python/Xkeen UI, нагрузку CPU/uptime и сообщения OOM. На 512 МБ — отдельные испытания, см. п. 6.
3. Определить текущую роль: маршрутизатор или AP, WAN/DHCP, upstream, LAN, политики устройств, DNS-фильтры и реального провайдера. **Подключение PORTABLE к LAN WORK для настройки — временный upstream, а не доказательство постоянной политики Ростелекома.** Двойной NAT и одинаковые подсети требуют проверки.
4. Аудировать текущие XKeen/Xray/FreeNet, веб-панели, subscription, маршруты DIRECT/VPN, DNS ownership порта 53, старые cron и автозапуски. Ничего не удалять до сохранения настроек.

### Шаг 1. Штатная установка UI

1. Сверить актуальный официальный release и документацию *на дату установки*. На HOME/WORK поставлен **3.0.2**; не заявлять, что он навсегда последний. Установка из официального `xkeen-ui-routing.tar.gz` только после проверки `.sha256` и подходящей архитектуры.
2. **Сохранить существующие исправные XKeen/Xray и учётные данные.** В режиме недостаточной ОЗУ рассмотреть официальный профиль `XKEEN_UI_INSTALL_PROFILE=xray-minimal sh install.sh`; в нём предусмотрены `core`, `engine.xray` и облегчённый `tool.editor`. **После установки проверить наличие необходимых функций подписок/routing/DNS в UI**, а не считать профиль эквивалентом Full без теста.
3. Если Xkeen UI уже установлена — использовать штатный профиль/обновления; не переустанавливать основное ядро. Не включать необязательные компоненты Happ/Mihomo/тяжёлые служебные функции без потребности. `xk-geodat` ставится по необходимости и с учётом ARM64/MIPSLE.
4. Проверить локальный HTTP 8088 и первый логин; внешний доступ — отдельно, только безопасным способом.

### Шаг 2. Подписка, маршруты и штатный балансировщик

1. Добавить **свою** подписку BlancVPN в официальном UI, не переносить чужой URL. В нашей конфигурации: hourly refresh, `transport_filter=^tcp$` → остаётся **50 TCP/REALITY**, исключается **6 WS**. Количество проверять по реальной подписке — оно может измениться.
2. В штатном UI выбрать режим переноса VLESS правил на балансировщик (`migrate-vless-rules`), **не** режим «поставить VPN-правило поверх всех DIRECT». Проверить порядок правил: DIRECT/исключения; затем VPN для сервисов и заблокированных адресов; общий VPN трафик; `balancerTag=proxy` / `leastPing`.
3. Observatory: 60 секунд. `fallbackTag` — *существующий исправный VLESS*, **не `direct`**; нельзя допустить утечки VPN трафика при отказе всех серверов.
4. ISP routing policy: Владлинк / АльянсТелеком — YouTube DIRECT; Ростелеком — YouTube VPN; Подряд — отдельная диагностика; Custom — по реальным требованиям. Прочие доменные и IP правила **сохранять из действующей конфигурации**, не придумывать.
5. Проверить действующую конфигурацию и `xray run -test`; штатный `xkeen -restart` только с обратимым изменением. Тестировать реальный egress, а не только состояние «VPN active» в UI. Учитывать GeoIP/DIRECT исключения при выборе контрольного IP: разные сайты проверки IP могут идти разными маршрутами.

### Шаг 3. Hybrid — без предупреждений панели

1. Проверить Xray `03_inbounds.json` и соответствие штатному пресету Hybrid. **Принятый эталон HOME/WORK: TCP `redirect` + UDP `tproxy`, порт 61219**.
2. На WORK первоначально работал custom Hybrid с портом **5000** и отличным от пресета sniffing; панель его справедливо классифицировала как «пользовательский». **Не лечить одно предупреждение слепой сменой порта**.
3. Для миграции проверить штатный пресет `MIXED_INBOUNDS` из установленной версии Xkeen UI на копии confdir → `xray run -test` → сохранить прежний `03_inbounds.json` → применить пресет **вместе со штатным `xkeen -restart`**, который считывает актуальный порт из inbound. Убедиться, что TCP/UDP слушают 61219, NAT Redirect и mangle TProxy направлены на 61219, старые правила 5000 отсутствуют.
4. Проверить DIRECT/VPN egress, DNS и HTTPS, в случае дефекта немедленно вернуть предыдущий рабочий JSON и перезапустить XKeen. Не копировать сетевые интерфейсы/политику/iptables HOME в другое устройство.

### Шаг 4. DNS-over-VLESS вместо FreeNet Split DNS

1. **Прочитать** нынешние `02_dns*.json`, `03_inbounds.json`, `04_outbounds*.json`, `05_routing.json`. Старые FreeNet DNS-only объекты могут конфликтовать со штатным UI: устаревшие `dns-vless`, `dns-direct`, `dns-out`, старый порт 53 и маршрутизация. Сначала протестировать **кандидат без конфликтующих legacy объектов** на копии, не сносить вслепую действующий DNS.
2. Настраивать только **штатную функцию DNS-over-VLESS Xkeen UI**, не добавлять отдельный dnsmasq/прокси. VPN upstream через VLESS, DIRECT через заранее **проверенные** резолверы; актуальная единая пара HOME/WORK — базовый Яндекс `77.88.8.8:53` + `77.88.8.1:53`. Если сеть требует другие адреса — не подменять без диагностики.
3. DNS inbound правильный — **`dns-in`** (не старый `dns-vless`). `opkg dns-override` освобождает порт 53 для Xray. Локальные Keenetic имена через резолвер прошивки только после реального DNS probe. `pass_non_ip=True` через существующий отдельный VLESS (не балancer); `dns.hosts` выключен.
4. DNS capture: в UI выбирать устройства по политике. На HOME/WORK по отдельному распоряжению пользователя настроены **все** 36/45 зарегистрированных, в том числе offline; **на PORTABLE и у мамы выбирать по их реальному инвентарю**. Не переносить MAC и не заставлять IoT автоматически менять свои специальные DNS без оценки.
5. После применения сверить **сохранённые MAC**, `client_report().counts.reaches`, реальное `iptables -t nat -S XKEEN_UI_DNS`, порядок перехода в `PREROUTING`, порт 53 TCP+UDP и DNS A/AAAA/MX/TXT, локальные имена. После изменений политик Keenetic цепочки могут перестраиваться; штатная Xkeen UI имеет собственный сторож/восстановление. Нельзя добавлять самодельный cron/watchdog.

### Шаг 5. GeoDAT строго штатным XKeen, затем удаление FreeNet

- Официальный файл `/opt/etc/xkeen/xkeen.json`: `xkeen.xray.geofile_update=true`, а `xkeen.xray.geodata[]` содержит ровно две ссылки на **RunetFreedom release**: `geosite.dat` из `runetfreedom/russia-blocked-geosite` и `geoip.dat` из `runetfreedom/russia-blocked-geoip`. Не добавлять Xray `08_geodata.json` с самостоятельной загрузкой.
- Одно активное root cron-задание на каждой площадке: `10 4 * * 1 /opt/sbin/xkeen -ug` — **понедельник 04:10, локальное время конкретного роутера**; штатный Entware `crond` активен. Это **не** FreeNet cron. XKeen может перезапустить Xray после обновления DAT — проверить краткий перерыв/восстановление.
- `xray/dat` не чистить по имени файла: каждая фактически используемая `ext:...dat:...` база остаётся. В частности WORK `zkeenip.dat` обслуживает YouTube/VPN.
- **Только после приёмки** остановить и удалить FreeNet 0.8, старую Xkeen UI, старые HTTP proxy 1000/1001, `update-geodata.sh`, их cron/init/logs. На WORK исторические резервные cron файлы выведены из активной `/opt/etc`; старые FreeNet дубликаты архивов очищены. При этом не удалять официальный `S05xkeen`, `S05crond`, Xray, штатную Xkeen UI, `xkeen -ug` и существующие проверенные credentials.

## 4. Полная приёмка — до и после изменений

- Xray стартует, `Configuration OK`, один процесс; **XKeen и панель 8088** живы; нет конфликтных слушателей DNS/Hybrid.
- TCP Redirect/UDP TProxy совпадают с активными inbound **и** iptables; нет прежнего 5000, если принят 61219.
- BlancVPN действительно используется VPN-правилами, 50 TCP при текущем формате подписки, `leastPing` и fallback VLESS; DIRECT сервисы реально идут DIRECT по политике данного ISP; YouTube отдельно.
- DNS через Xray: A/AAAA/MX/TXT/SRV и Keenetic hostname, `dns-in`, direct resolver и VPN DNS path; DNS capture совпадает со списком устройств и не блокируется прошивкой.
- HTTPS YouTube, Apple, GitHub, Telegram — 200; Cloudflare generate_204 — 204. Замерить задержки/полную загрузку, не считать один HTTP статус гарантией отсутствия лагов.
- Проверить реальные устройства, звонки/WebRTC, обработку обрыва VPN, ночного обновления GeoDAT и перезагрузки роутера. Отдельно проверить, не открыта ли панель слишком широко наружу.
- При отказе: вернуть предыдущую рабочую конфигурацию, валидировать `xray -test`, штатно рестартовать XKeen и убедиться, что DNS/HTTPS и доступ к UI восстановились. **Не оставлять полуприменённый DNS или отключённый интернет.**

3. HOME: периодическая перестройка PREROUTING при Policy0/UPnP; штатная Xkeen UI восстанавливает DNS capture. Следить за фактическими `client_report` и порядком iptables, не отключать UPnP без проверки.
4. WORK: проверка 45 устройств/IoT после их фактического включения, а не только по сохранённому списку.
5. Первый плановый запуск **09.11.2026, 04:10 по времени каждого роутера** нужно проверить *после факта* (DAT timestamps, Xray, DNS, HTTPS). До него расписание проверено, но не само недельное скачивание.

## 6. PORTABLE и Ultra с 512 МБ — план управления памятью

**По сообщению владельца:** PORTABLE — **Keenetic Giga, 512 МБ**; у мамы — **Keenetic Ultra, 512 МБ**. Точный KN-номер пока не подтверждён. По официальной спецификации **Giga KN-1011** имеет MIPS MT7621 + 512 МБ; другие ревизии Giga/Ultra могут иметь иную архитектуру или размер памяти — **не угадывать бинарники по слову «Giga» или «Ultra»**.

**Реальный замер HOME 08.11.2026:** `MemTotal=991 MiB`, `MemAvailable=468 MiB`, `Cached=265 MiB`, RSS Xray ~105 MiB, суммарный RSS процессов Python ~90 MiB, swap ~478 MiB не использовался. Поэтому «в панели 50–52% RAM» **не доказывает**, что DNS-over-VLESS не уместится в 512 МБ: кэш освобождаем. Но гарантий также нет — CPU и 50 Reality-узлов/Observatory на MIPS могут стать ограничением раньше ОЗУ.

**Перед установкой и после неё:** снять память доступную ОС и RSS по процессам, CPU/load, число активных узлов, OOM/dmesg, задержку DNS/HTTPS. Проверить, что Entware живёт на внешнем USB, хватает места, CPU архитектура поддерживается официальными release. Сначала сохранить существующие VPN/DNS и доступ.

**Контрольные ориентиры проекта, не обещания разработчика:** устойчивый запас `MemAvailable` **желательно ≥96–128 MiB** после прогрева и типичной нагрузки, без OOM, бесконечного swap I/O и роста RSS; при падении ниже ~64 MiB, высоких задержках или OOM — **не включать дополнительную нагрузку**, откатить последнюю настройку и разбирать узкое место. Swap может помочь от пиков ОЗУ, но **не** замена достаточной RAM и не повод устраивать постоянные записи на USB.

**Если ресурсы ограничены:** (1) использовать существующий здоровый XKeen/Xray, не переустанавливать; (2) штатный профиль Xkeen UI `xray-minimal` (официальный `core, engine.xray, tool.editor(light)`; DNS-over-VLESS принадлежит engine.xray, но после установки проверить реально доступную карточку/службу); (3) отключить только ненужные *штатные* дополнительные компоненты (Mihomo/Happ/декораторы), **не** DNS сторож и не действующий VPN; (4) проверить необходимость числа узлов/частоты Observatory **до** уменьшения — цель стабильность, не экономия ради цифры. Если штатный DNS-over-VLESS не выдерживает реальные тесты — оставить работающий DNS Keenetic/ISP и зафиксировать **ограничение конкретной площадки**, не внедрять FreeNet Split DNS.

**PORTABLE завтра:** подключить Giga к WORK только после определения его WAN/LAN IP, избежать конфликта подсетей и double-NAT ошибок; определить его собственную будущую ISP-политику, не скопировать Ростелеком автоматически; проверить baseline RSS до установки; проверить выбранный официальный установочный профиль и RAM; далее шаги 1–5 и полная приёмка. **Мамин Ultra — отдельный повтор с её собственными условиями/провайдером**, не обещать успех до замера.

---

**Статус FreeNet:** исторический архив кода и CI, **не продукт для дальнейшего развития/установки**. Новые задачи вести в отдельном issue о переходе на Xkeen UI. Финальное архивирование репозитория — только после завершения миграции PORTABLE и роутера у мамы, чтобы сохранить доступ к журналу и инструкции.
