# FreeNet Router v0.8.0-beta.77

## Что изменилось

### AutoVPN — короткий карантин подтверждённо отказавших серверов при аварийном восстановлении

- При повторных подтверждённых отказах некоторых VPN-кандидатов аварийный AutoVPN раньше мог снова затратить часть ограниченных проверок на те же нерабочие логические выходы. На HOME beta.75 ранее наблюдалась цепочка Czech → Denmark → Austria за примерно 10 минут и неудачный поиск замен. Непосредственная причина каждого переключения и качество Reels на конкретной площадке требуют отдельной аппаратной приёмки.
- В аварийном подборе на **5 минут** запоминаются только кандидаты, для которых **два полностью завершённых независимых HTTPS-раунда через изолированный VLESS-профиль** не подтвердили работу приложения. Один неуспешный RTT, timeout, отменённая или неоднозначная проверка, занятый изолированный Xray и неизвестный результат **не объявляют сервер неисправным**.
- Память хранит ограниченное число SHA-256 идентификаторов точного VLESS URI **только в RAM**: без публикации UUID, Reality-полей, ключей, subscription URL или сырой конфигурации. Разные логические выходы, даже если у них общий IP:port, не смешиваются; после успешной свежей проверки либо истечения TTL карантин снимается.
- При аварийном подборе сначала проверяются свежие разрешённые ISP/country policy кандидаты. Недавно отказавшие сохраняются **как резерв**: если свежих альтернатив недостаточно либо нет, они проходят новый полноценный HTTPS admission. Карантин не должен полностью лишать пользователя возможности восстановить VPN.
- Ограничение до 8 кандидатов за поиск, страна ручного выбора, курсор по подписке, one-hour anti-flap для media-only, single-flight, snapshot, provider guarded apply, post-apply acceptance и rollback/STOP сохранены. Никаких автоматических смен DNS/ISP/routing, переписывания XKeen/Xray и скрытых shell-tasks не добавлено.

### Диагностика — неизвестный VPN-пинг больше не выглядит как 0 мс

В аварийном summary при отсутствующем измеренном RTT выводится **«VPN не измерен»**, а не вводящее в заблуждение `VPN 0 мс`. Application HTTPS latency и диагностические счётчики сохранены.

## Что этот релиз НЕ доказывает

**beta.77 не является подтверждением отсутствия буферизации Instagram Reels/Telegram.** Management сообщил, что через отдельное VPN-приложение видео воспроизводится нормально, а через роутер бывает медленнее. Это требует отдельного сравнения фактического клиентского маршрута VPN/DIRECT, выходного сервера, DNS/CDN, UDP/QUIC и непрерывного переноса видеоданных; обычные HTTPS/Speedtest пробы не воспроизводят Instagram Reels.

Релиз меняет FreeNet-owned UI/backend, но не перезаписывает текущие Xray/XKeen или пользовательские ISP/DNS/routing, subscription и секреты. Публикация GitHub Release **не устанавливает** версию на роутер.

## Порядок безопасной приёмки

1. Публиковать только после release-only PR terminal CI SUCCESS, merge, Release CI terminal SUCCESS и сверки exact tag SHA, `SHA256SUMS` и release assets.
2. Management подтвердил beta.76 на HOME, WORK, MOM. До нового отдельного безопасного плана **не обновлять HOME/MOM автоматически и не выполнять искусственных аварийных переключений**; WORK использовать для назначенной canary только после штатных updater/rollback preflight и без исторического `UNKNOWN`/STOP. Portable `FAILED_UNKNOWN` остаётся STOP.
3. После разрешённого обновления: terminal updater receipt, Xray/XKeen/DNS state, VPN transaction doctor, read-only AutoVPN события (quarantined/fallback/«VPN не измерен»), реальный клиентский HTTPS egress и наблюдение воспроизведения видео. При FAIL/UNKNOWN/ROLLBACK FAILED — STOP, без повторных apply.
4. Следующая отдельная задача: диагностировать клиентскую QoE разницу «отдельное VPN-приложение против роутера», не смешивая её с аварийным карантином.
