# FreeNet Router v0.7.13 — диагностика подключения OpenAI Tunnel без SSH

## Что изменилось

### Исправлено: «RUNNING_NOT_READY» без объяснения причины

- На реальном Keenetic/Netcraze с FreeNet v0.7.12 tunnel-client v0.0.16 после штатной установки, сохранения ограниченного Runtime API key и запуска оставался `RUNNING_NOT_READY`; текущий экран показывал только `/readyz` (не подтверждён), без причин.
- Начиная с **v0.7.13**, кнопка **Администрирование → OpenAI Tunnel → «Проверить туннель»** дополнительно читает документированный **локальный** `http://127.0.0.1:12031/health?details=true` официального OpenAI tunnel-client v0.0.16 и показывает компоненты `control-plane`, `mcp`, `oauth`, `cloudflared`, `response-delivery`.
- Для control-plane отображаются безопасные признаки: `status`, `state`, `reason_code`, `failure_category`, числовой HTTP-код и число последовательных ошибок, если они присутствуют. Для MCP отображается стадия `startup_probe`, если она наблюдалась.
- Если health endpoint недоступен, вернул неожиданный JSON, HTTP-ошибку или неизвестную схему, FreeNet выводит `UNAVAILABLE`, `HTTP_UNAVAILABLE` либо `INVALID_HEALTH`, а не сообщает ложную готовность и не угадывает ошибку. `/readyz` не считается подтверждением ChatGPT end-to-end.

### Безопасность

- Только существующая авторизованная сессия FreeNet Control Center может вызвать новый `GET /api/admin/connector/tunnel/health`.
- Источник закреплён как **127.0.0.1**, нет произвольных URL, перенаправлений или наследуемых HTTP-прокси; таймаут 1,6 с, ограничение тела 64 KiB.
- Наружу выводятся только отобранные поля предопределённого формата. Полные ответы сервера, ошибки, URL, токены, идентификаторы туннеля, секретные заголовки и подробные конфигурации не копируются в браузер или GitHub.
- **Никаких операций изменения состояния:** диагностика не устанавливает и не перезапускает клиент, не меняет OpenAI-ключ, Xray, VPN, DNS, firewall, routing или SSH.
- Показываемые компоненты — снимок наблюдений клиента, а не самостоятельная проверка реальной связи ChatGPT. Результат `control-plane: ok` ещё не означает, что пользовательский MCP-плагин подключён.

### Проверки

- [PR #1119](https://github.com/VoltickVL/FreeNet-Router/pull/1119) (Execution Issue #1118): read-only parser/projection, безопасный loopback HTTP, admin-auth и browser regression. **CI terminal SUCCESS 5/5** на exact HEAD `b6b6b76f2c24f19604a6a94c33c599592541b302`; merged stable SHA `36e22de1669d1e157211a9bf8639292b3802ecfb`.
- На первой попытке CI старый тест Config Studio показал известную STALE-гонку; после анализа Actions выполнен один точечный rerun только сбойного задания на том же SHA → SUCCESS. Код Config Studio не менялся.
- **Runtime-приёмка v0.7.13 ещё не выполнялась.** Пока неизвестно, от чего OpenAI tunnel-client на реальном роутере находится в `RUNNING_NOT_READY`.

## Что сделать после обновления

Обновить FreeNet штатно с 0.7.12 до 0.7.13 в Control Center → открыть «Администрирование» → «OpenAI Tunnel — подключение ChatGPT» → **один раз** нажать «Проверить туннель». Прислать только несекретный вывод компонентов. **Не нажимать «Запустить», «Остановить», «Забыть ключ» и не переустанавливать клиент ради повторной диагностики**.

По полученному `control-plane` / `mcp` состоянию исполнитель определит PRIMARY ERROR, а затем спланирует минимальное исправление; без SSH-обходов. Только после подтверждённой готовности и авторизации — регистрация пользовательского ChatGPT MCP-плагина и проверка `initialize`, `tools/list`, `request_access`, owner approve, `get_status`, revoke.
