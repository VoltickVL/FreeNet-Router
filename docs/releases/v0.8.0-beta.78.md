# FreeNet Router v0.8.0-beta.78

## Что изменилось

### Диагностика видеолагов Instagram Reels и Telegram — без SSH

В Control Center → «Настройки» появился сворачиваемый раздел **«Видео и связь — диагностика»**. Выберите Instagram Reels или Telegram и нажмите **«Снять диагностическое состояние»**.

- По одному нажатию FreeNet получает защищённый авторизацией **read-only** снимок: состояние правил перехвата TCP/TPROXY и kernel routing, исключения LAN, сконфигурированный режим DNS и последнюю завершённую запись контроля VPN с временем. Используются уже существующие внутренние источники; новые фоновые проверки и загрузки видео не создаются.
- Диагностика никогда не переводит наличие установленного правила перехвата или работающего Xray в утверждение «сервис на клиенте работает». **Клиентский VPN/DIRECT egress, реальный DNS/CDN путь, UDP/QUIC и playback показывают UNKNOWN**, пока отдельные фактические проверки не подтвердили их. Одного HTTP 200, успешного Speedtest или здорового watchdog недостаточно для приёмки Reels.
- API `GET /api/qoe/incident?service=instagram|telegram` требует обычной авторизованной сессии Control Center. Метод POST отсутствует. В ответе фиксированные безопасные enum, UTC timestamp, `mutation=NONE`; не включаются IP/MAC устройств, пароли, UUID/Reality, subscription URL, сырые правила netfilter и приватные журналы. Некорректная или отсутствующая информация остаётся UNKNOWN.
- Диагностическая карточка свёрнута по умолчанию, использует действующие UX-правила Control Center, а результаты выводятся текстом, без HTML-инъекции.

## Что выяснено до релиза

04.11.2026 на единственном доступном через подключённый iMac шлюзе FreeNet независимым read-only HTTP подтверждена **beta.77** и `/healthz=ok`. HTTP/2 Instagram и Telegram отвечали 200, Cloudflare `loc=IT` для IPv4 и IPv6; отдельные RTT/TTFB получены, но **это не реальные тесты Instagram Reels или видео Telegram**. Локальный IPv4/IPv6 тест не доказал географического расхождения выходов. Protected FreeNet API нельзя использовать без авторизации; браузерный connector требует исходного браузерного контекста. Полное аппаратное состояние HOME/WORK/MOM и client QoE остаются непроверенными.

## Scope, тесты и безопасность

- [Issue #1333](https://github.com/VoltickVL/FreeNet-Router/issues/1333) → [PR #1334](https://github.com/VoltickVL/FreeNet-Router/pull/1334), кодовый merge `e34d61375271224adaf6783c880f335f21e955ff`.
- Кодовый PR изменил только четыре файла: `main.go`, новый `qoe_incident.go`, новый `qoe_incident_test.go`, `web/settings-v3-core.js`.
- Финальный source HEAD `8396909303b3be05c5a21387bc96d0664db0affd`. Router, Routing, Config Studio и Production Browser CI завершены успешно. Ранний Settings Browser CI упал из-за отсутствовавшего collapse у новой карточки; исправлено в коде после чтения реального лога. Production Browser CI на финальном HEAD дал timing-sensitive failure в старом manual VPN reconciliation fixture, затем успешно прошёл один диагностический повтор конкретного job на неизменённом HEAD; исходная timing-причина отдельно не доказана.
- Нет изменений текущих ISP/DNS/routing policies, Xray/XKeen, подписок, SSH, автопереключений, обновляющего механизма или rollback. При получении snapshot роутер не делает никаких mutations.

## Что дальше

**beta.78 — первая ступень наблюдаемости, а не обещанное устранение буферизации.** Основная пользовательская цель — непрерывный Instagram Reels и Telegram через роутер, сопоставимый с отдельным VPN-приложением — остаётся открытой. Следующий отдельный цикл: собрать доказательство фактического per-client VPN/DIRECT egress, DNS/CDN и UDP/QUIC с видео, установить PRIMARY ERROR, затем выполнить минимальное исправление с тестами и защищённым откатом. Не считать Split DNS обязательным и не покупать новые Netcraze Ultra без доказанного аппаратного ограничения.

Management ранее сообщил beta.76 на HOME/WORK/MOM, позже локальный iMac подтвердил beta.77 **на одном доступном шлюзе без точной привязки к площадке**. Публикация beta.78 не является её установкой. Не проводить автоматических rollout/переключений на HOME/MOM и Portable, где сохраняется `FAILED_UNKNOWN STOP`. Актуальная испытательная площадка определяется только прямым указанием Management и состоянием безопасного preflight.
