# FreeNet v0.8.0-beta.65

## Что изменилось

### P0: защищённое восстановление XKeen 2.1 на работающем роутере

- [PR #1292](https://github.com/VoltickVL/FreeNet-Router/pull/1292), merge `554df6d6bf3c23c54cadc8c584dbf6ce6e9eb239`, 4/4 terminal PR CI SUCCESS.
- Для **единственного доказанного** сценария старого XKeen init и netfilter hook при аварийном `VPN checkpoint=PENDING` существующий экран **Xray → Восстановить автозапуск XKeen** теперь допускает адресную ремонтную транзакцию. Требуются одновременно: совпадение всех VPN файлов с защищённым снимком, Xray остановлен, не исполняется другой probe или production, отсутствуют неизвестные/zombie процессы и write-lock, native XKeen Stable 2.1 и именно legacy hook `03_info_cpu.sh`. Любое другое состояние = STOP без изменения.
- До первого нативного изменения FreeNet сохраняет в закрытой директории (режим 0700) независимые снимки init.d и **полного старого netfilter `proxy.sh`** (режим 0600). Сохраняет долговечную фазовую квитанцию `INIT_REBUILD → START → DONE`. Штатно вызывает XKeen `-ri` для пересоздания автозапуска с сохранением upstream-преемственности; затем допускает **только один** контролируемый `-start` внутри этой операции.
- Перед запуском и после него выполняется проверка семантики текущей Xray-конфигурации без вывода секретов. После запуска требуются один подтверждённый Xray production, отсутствие посторонних/probe/zombie процессов, генерация современного netfilter hook и сохранённый, не удалённый original VPN checkpoint, все исходные VPN файлы совпадают со снимком.
- Вне этой специальной операции никакие service/start/stop/restart, VPN profile apply, updater или автооперации при `PENDING/UNKNOWN` **не разрешаются**. При сбое файлы init/hook восстанавливаются по снимкам, а если нативные `-ri` или `-start` уже могли изменить firewall или ports, rollback **UNKNOWN=STOP** даже при совпадении байтов. Ложных `SUCCESS` не бывает.
- Новые тесты: PENDING allowlist, запреты при drift, owner-lock/foreign/unknown/zombie/probe, временная копия legacy netfilter с проверкой byte-for-byte, отклонение symlink и отсутствующего/современного hook.

### Аппаратная приёмка Work отдельно

На реальном Netcraze Ultra с предыдущей beta.64 до этого обновления авторизованный `/api/xray/core/read-only-test` подтвердил `valid=true`, `netfilter_hook=legacy-removed-module-reference`, `xkeen_init=legacy-init-references-removed-module`; `/api/vpn/transaction-doctor`: `checkpoint=pending`, три файла matched, Xray stopped. Это подтверждённая несовместимость legacy init, но **не подтверждение восстановленного VPN**.

**Установка beta.65 сама по себе не запускает Xray, не очищает аварийный checkpoint и не переключает VPN-сервер.** Только после успешного штатного FreeNet self-update и нового read-only plan выполняется одна отдельно подтверждённая repair-транзакция через Control Center. Далее обязательны terminal result, Xray process inventory, live HTTPS acceptance, проверка original checkpoint и отдельная фиксация rollback. Если FAIL/UNKNOWN — STOP; никаких ручных удалений `proxy.sh`, WebCLI shell mutations, reboot или повторного apply.

### Совместимость

Keenetic/Netcraze с Entware + существующие XKeen 2.1 Stable и Xray. Подписка, credentials, ISP/DNS policies и конфигурация Xray сохраняются. Не создаётся терминал SSH внутри Control Center. [Постоянная задача P0 #1227](https://github.com/VoltickVL/FreeNet-Router/issues/1227) остаётся открытой до аппаратной приёмки.
