# FreeNet Router v0.7.14 — OpenAI Tunnel только через VPN Xray

## Что изменилось

### Исправлено: исходящий OpenAI tunnel-client обходил обычные LAN-правила

- По запросу Management устранена архитектурная неоднозначность исходящего трафика **самого роутера**: штатный OpenAI `tunnel-client v0.0.16` отправляет control-plane HTTPS через локальный HTTP CONNECT шлюз **Xray VLESS Reality**, а не через прямой маршрут российского ISP.
- FreeNet создаёт **отдельный временный Xray-процесс**, слушающий только `127.0.0.1:12032`. Он собирается из **единственного** существующего outbound с тегом `vless-reality` текущего конфигурационного каталога Xray. В отдельной конфигурации нет `direct` / `freedom` outbound и нет запасного маршрута на случай проблем с VPN.
- Перед запуском tunnel-client обязательны: факт работающего основного Xray, чтение и проверка структуры текущего VLESS Reality-профиля, проверка отдельной Xray-конфигурации штатным `xray run -test`, свободный loopback-порт, запуск вспомогательного процесса и успешный **HTTP CONNECT к `api.openai.com:443` через VLESS**. Любое UNKNOWN / FAIL означает STOP **до запуска** tunnel-client; DIRECT не используется.
- Используется **точно `control_plane.http_proxy`** официального tunnel-client, а не общий `http_proxy`. Обращения tunnel-client к локальному FreeNet MCP остаются на `127.0.0.1`, через внешний VPN они не уходят.
- Сетевые переменные окружения, которые могли бы переопределить YAML-настройку и привести к неконтролируемому обходу proxy, исключаются из окружения дочернего tunnel-client. Отдельный Xray-процесс помечен так, чтобы не считаться основным рабочим Xray в диагностике FreeNet.
- Существующие Tunnel ID, restricted Runtime API key и локальный Bearer **не перезаписываются и не ротируются**. Установленный в v0.7.12–.13 YAML распознаётся по **точному совпадению** и безопасно мигрирует на фиксированный control-plane proxy. Изменённый вручную либо неизвестный конфиг не перезаписывается: STOP.
- Приватная временная копия VLESS outbound хранится с правами `0600` в закрытом каталоге FreeNet и удаляется при штатной остановке. Запущенный основной Xray/XKeen, рабочие VPN-профили, DNS, firewall и правила маршрутизации остальных устройств не изменяются.
- В **Администрирование → OpenAI Tunnel → Проверить туннель** отображается индикатор VPN-only egress. Временный доступ к диагностике ChatGPT по-прежнему требует отдельного разрешения Management.

### Почему это исправление необходимо

На реальном ARM64 Keenetic/Netcraze Management наблюдал FreeNet v0.7.13, Xray v26.9.9, VPN Италия, DNS раздельный, запущенный `tunnel-client v0.0.16`, но readiness FALSE. Компонентная диагностика показала `control-plane=degraded/backoff`, **HTTP 403**, 7 ошибок подряд; MCP startup `failed`.

Сам по себе **HTTP 403 не устанавливает причину**: это может быть как отклонение запросов вследствие ограничений сети, так и отсутствие у principal API-ключа права **Tunnels Use на конкретный туннель**. Настоящая причина будет установлена после пробы control-plane через подтверждённый VPN-путь. Никаких новых API-ключей и переключения маршрутов вручную на этом этапе не требуется.

### Проверки и границы

- **Source [PR #1122](https://github.com/VoltickVL/FreeNet-Router/pull/1122)** / [Issue #1121](https://github.com/VoltickVL/FreeNet-Router/issues/1121): exact HEAD `368752172ac1b7bbceb93bbb328fc840f2d0c673`, base `7c311b6aa78217fb054b19bd4cda9b9a6b3198b1`, merge SHA `02b9f5e97b56788bdab2d1df6719a9fb7a0348b5`, **terminal CI SUCCESS 5/5**. Scope 6 файлов: isolated VPN-only Xray sidecar, lifecycle/legacy migration, status UI и Go/browser regression tests.
- Unit-тесты проверяют Xray JSONC, строгий единственный outbound VLESS Reality, отсутствие DIRECT в конфигурации, необходимость loopback HTTP CONNECT, отказ при неизвестных профилях/симлинках, безопасную миграцию локального YAML без изменения OpenAI credentials, защиту от подмены конфигурации переменными окружения и локальность MCP.
- В рамках GitHub PR и релиза **не выполнялись изменения реального роутера**, не запускались SSH/ручные shell-команды и не отправлялись секреты в GitHub.
- **Runtime acceptance ещё не проведена**: этот Xray-sidecar и настоящий CONNECT через реальный итальянский VPN на ARM64 роутере до установки v0.7.14 не проверены. SUCCESS CI не означает, что OpenAI/ChatGPT уже подключены.
- Не утверждать, что `vpn_egress_process_active` доказывает end-to-end ChatGPT. End-to-end нужно подтвердить отдельно через ChatGPT MCP.

## Что делать после обновления

1. **Штатно обновить FreeNet v0.7.13 → v0.7.14** через Control Center, без переустановки tunnel-client и повторного ввода ключа.
2. В «Администрирование» → OpenAI Tunnel нажать **«Проверить туннель»** и посмотреть VPN-egress / `client_running` / `client_ready` / `control-plane HTTP` / `mcp`. Если FreeNet остановился с `VPN_...` — НЕ повторять вслепую запуск, не делать SSH/ручных Xray правок, сообщить конкретный error code.
3. Если VPN-egress подтверждён и `control-plane` становится OK — подключить уже созданный в OpenAI Platform туннель FreeNet Router в ChatGPT Plugins (Tunnel / No authentication), проверить `initialize`, `tools/list`, `request_access`, admin approval, read-only `get_status` и revoke.
4. Если реальный OpenAI **HTTP 403 сохраняется при подтверждённом VPN CONNECT**, отдельно сверить RBAC/organization principal и per-tunnel Tunnels Read+Use. Нельзя объявлять это ошибкой VPN без фактов.

До завершения runtime-проверки доступ ChatGPT к роутеру считается **НЕ ПОДКЛЮЧЁН**.
